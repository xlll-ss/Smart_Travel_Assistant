## 1. 项目速述

### 1.1 30 秒介绍模板

我实现了一个基于本地 Ollama、HelloAgents、Gradio、SQLite 和 RAG 的智能旅行助手。它会先根据问题判断是否需要地点检索、天气、路线或攻略知识库，再把用户偏好、候选地点、实时数据、RAG 片段和最近对话组合成上下文，让本地模型生成结构化 JSON 行程。为了防止模型违反室内偏好、预算、总时长或编造地点，我没有只依赖提示词，而是在 Python 中做了候选白名单和硬约束二次校验，并为模型连续输出违规结果设计了确定性降级方案。

### 1.2 2 分钟介绍模板

这个项目解决的是“自然语言旅行需求如何可靠地落到可执行行程”这个问题。用户可以填写城市、出发地、心情、室内外偏好、预算、可用时间和同行方式，也可以导入 PDF、Markdown、TXT 或粘贴个人攻略。

一次请求先进入 `TravelToolRouter`。路由器通过本地 LLM 判断是否调用地点、天气、路线和知识库工具；如果模型路由失败，则退回关键词规则。地点推荐不是让模型自由生成，而是由 `PlaceCatalog` 从 SQLite 地点目录中按照城市、环境、预算和时长先做确定性过滤。天气使用 Open-Meteo，地点解析使用 Photon，驾车路线使用 OSRM，攻略通过本地 RAG 检索。

随后 `TravelAssistant` 把系统规则、最近三轮历史、用户偏好、候选白名单、实时工具事实和 RAG 证据组装成 messages，调用 `HelloAgentsLLM.invoke()` 请求 JSON。模型返回后，程序再次校验地点白名单、预算、室内外偏好、单项字段和总时长。如果第一次结果不合法，会把错误原因和允许地点列表反馈给模型修正；第二次仍失败，则由程序基于可信候选生成保守方案。

数据方面，地点和偏好存入 SQLite，对话历史放在 Gradio 会话状态中，每个用户的 RAG 数据使用独立数据库命名空间。PDF 使用 Docling 解析为带物理页码、章节和表格信息的内容块，使用本地 BGE 生成语义向量，检索后把来源位置同时交给模型和页面。项目还包含日志轮转、安全错误编号、认证检查和约束评测集。最近验证的默认测试结果为 30 passed、2 skipped；启用真实 PDF 解析测试后为 31 passed、1 skipped，剩余跳过项为真实 Ollama 测试。这些结果验证当前测试覆盖的行为，不能等同于检索准确率或并发容量。

### 1.3 一句话技术亮点

> 把 LLM 当成受约束的规划器，而不是事实数据库：工具提供事实，Python 执行硬约束，模型负责理解意图和组织表达。

## 3. 项目设计面试题

### Q1：这个项目解决了什么问题？

回答要点：

- 普通聊天模型能给旅行建议，但容易编造地点、天气、票价和交通信息。
- 用户偏好包含硬约束，例如“只要室内”“预算经济”“只有 4 小时”。
- 项目把自然语言理解交给 LLM，把实时事实交给工具，把硬约束交给 Python。
- 最终目标不是生成一段看起来合理的文字，而是生成可校验、可展示、可追踪的结构化行程。

常见追问：为什么不用一个 Prompt 直接让模型回答？

- Prompt 是软约束，模型可能不遵守。
- 外部事实会变化，模型参数中的知识不是实时数据。
- 程序级校验可以自动测试，Prompt 很难提供同等确定性。

### Q2：为什么选择本地 Ollama？

回答要点：

- 不需要云端 API Key，适合学习、离线演示和隐私敏感数据。
- Ollama 提供 OpenAI 兼容接口，可以复用统一 LLM 客户端。
- 成本低，模型和数据留在本机。
- 代价是推理速度、结构化输出稳定性和模型能力受本机硬件限制。

追问：如何迁移到云端模型？

- 保持 `TravelAssistant` 不变，替换 `HelloAgentsLLM` 的 provider、model、base_url 和凭据。
- 重新跑结构化输出、工具路由和约束评测，因为不同模型行为不同。

### Q3：为什么使用 Gradio，而不是 Flask/FastAPI 加前端？

回答要点：

- Gradio 能快速构建聊天、文件上传、表格和表单，适合原型和作品集演示。
- 它自带事件绑定、队列和会话状态，降低前端开发成本。
- 当前限制是权限模型、页面定制和大规模部署能力有限。
- 如果产品化，会把 Agent 服务拆成 FastAPI，前端使用 React/Vue，并引入正式认证系统。

### Q4：为什么使用 SQLite？

回答要点：

- 项目是单机、小规模数据，SQLite 无需单独部署数据库服务。
- 支持事务、索引、WAL 和结构化查询，比 JSON 文件更可靠。
- 地点、偏好和 RAG 文本块都适合本地持久化。
- 多进程写入、高并发、复杂权限和大规模向量检索时应迁移到 PostgreSQL 与专用向量库。

### Q5：项目最重要的工程决策是什么？

回答要点：

- 将“模型建议”和“程序决策”分开。
- 地点先由程序过滤，模型只能从白名单中选择。
- 工具结果被包装成数据类，不把外部 API 原始 JSON 直接传遍系统。
- 模型输出必须经过解析、字段校验和业务约束校验。
- 每个用户的私有 RAG 使用独立命名空间，避免跨用户检索。

### Q6：这个项目算 Agent 吗？为什么不是普通聊天机器人？

回答要点：

- 它会根据输入动态选择工具，不是固定调用链。
- 它有状态：用户偏好、会话历史、地点库和知识库。
- 它会获取外部环境事实，并基于结果完成规划。
- 它有行动结果校验和失败降级。
- 但它不是完全开放式自治 Agent，而是一个受控、单轮工具路由加规划的领域 Agent。

### Q7：为什么没有直接使用通用 ReActAgent？

回答要点：

- ReAct 适合未知步骤、需要多次“思考—行动—观察”的开放任务。
- 旅行应用的工具集合和安全约束明确，固定编排更稳定、更容易测试。
- 当前实现保留了 Agent 的动态工具选择，但把最大循环次数、工具顺序和验证逻辑交给代码控制。
- 如果未来需要多轮查票、比较酒店、重新规划，可以引入状态机或 ReAct 图结构。

### Q8：为什么采用依赖注入？

回答要点：

- `TravelAssistant` 通过构造参数接收 LLM、地点目录、实时工具、知识库和路由器。
- 测试时可以注入假 LLM、静态地点目录或离线工具。
- 避免类内部偷偷创建全局资源，降低耦合。
- 便于替换 Ollama、数据库或外部 API，而不重写业务流程。

### Q9：项目中的数据源分别是什么？

回答要点：

- 用户输入：偏好、问题、上传攻略。
- 系统地点目录：人工维护的 SQLite 记录。
- 实时工具：Photon、Open-Meteo、OSRM。
- RAG：共享攻略和每用户私人攻略。
- 对话上下文：当前 Gradio 会话最近三轮。
- 模型输出不是事实数据源，只是基于上述材料生成的计划草案。

### Q10：当前项目有哪些边界？

回答要点：

- 当前使用 `BAAI/bge-small-zh-v1.5` 生成真实中文语义向量，但首次运行需要下载模型，CPU 编码长文档也有延迟。
- SQLite 检索会全量读取文本块并在 Python 中计算相似度。
- 公共 API 可能限流、超时或返回不准确地理位置。
- 路线只提供 OSRM 驾车估算，不是公交导航。
- Gradio 认证和共享地点管理不适合直接公开到互联网。
- 当前推荐单进程部署。

## 4. Agent 与 LLM 面试题

### Q11：一次用户问题的完整执行顺序是什么？

回答要点：

1. 页面值转换成 `TravelPreferences` 并校验。
2. `_limit_history()` 清洗并截断会话历史。
3. `TravelToolRouter.decide()` 生成工具调用计划。
4. 按需筛选地点、请求天气/路线、检索 RAG。
5. `build_messages()` 组合 system、历史和当前 user 消息。
6. `_request_answer()` 调用本地 LLM 获取 JSON。
7. `_parse_plan()` 校验结构和硬约束。
8. 首次失败时修正一次；再次失败时生成确定性保守方案。
9. 转成 Markdown，并把 user/assistant 消息写回当前会话历史。

### Q12：`think()` 和 `invoke()` 有什么区别？本项目为什么用 `invoke()`？

回答要点：

- `invoke()` 返回完整文本，适合需要一次性解析 JSON 的场景。
- `think()`/流式接口逐段产生 token，适合边生成边显示。
- 本项目必须等完整 JSON 返回后再解析和校验，所以核心流程使用 `invoke()`。
- 如果改成流式展示，不能在校验前直接把未完成或违规内容展示给用户。

### Q13：messages 中包含哪些角色？

回答要点：

- `system`：助手规则、用户偏好、工具决策、候选地点、实时事实和 RAG 证据。
- `user`：用户之前的问题和当前问题。
- `assistant`：之前已经展示给用户的回答。
- 当前问题必须位于最后，表示模型本轮需要处理的输入。

### Q14：为什么把候选、工具结果和 RAG 放进 system 消息？

回答要点：

- 它们属于应用提供的本轮约束和事实，不是用户自由文本。
- system 优先级高于普通 user/assistant 历史。
- 可以减少历史回答中的过期信息影响当前工具事实。
- 仍不能只靠消息优先级，所以输出后还要程序校验。

### Q15：为什么只保留最近三轮历史？

回答要点：

- 防止上下文无限增长，降低本地模型延迟和内存占用。
- 减少旧偏好、旧天气和旧路线污染当前回答。
- 三轮是当前经验参数，不是理论最优值。
- 更成熟的方案是按 token 预算截断，并对更早历史做摘要或长期记忆检索。

### Q16：`_history` 和 `gr.State` 有什么区别？

回答要点：

- 通用 Agent 基类可以把历史存在对象的 `_history` 中。
- Web 应用中的 `TravelAssistant` 是共享实例，如果把所有历史放进实例，会造成用户串话。
- 当前项目把历史交给 Gradio `gr.State`，每次请求显式传入并返回。
- 这是把状态从共享服务对象移到会话边界。

### Q17：路由模型返回什么？

回答要点：

```json
{
  "place_search": true,
  "weather": false,
  "routes": false,
  "knowledge": true,
  "reason": "用户要求根据攻略推荐地点"
}
```

- 程序验证四个工具字段必须存在且为布尔值。
- 路线依赖地点，因此 `routes=true` 时会强制 `place_search=true`。
- 对问候和纯天气问题还有程序规则二次修正。

### Q18：为什么工具路由还需要关键词 fallback？

回答要点：

- 本地模型可能超时、返回非 JSON 或字段错误。
- fallback 保证基础功能不会因路由模型失败而完全中断。
- 关键词规则是确定性的，方便测试。
- 它的缺点是语义理解有限，因此只作为降级，不是主要路由方式。

### Q19：为什么温度参数不同？

回答要点：

- 工具路由使用 `temperature=0`，需要稳定和可重复。
- 行程生成使用较低但非零温度，例如 `0.3`，保留一定表达灵活性。
- 无论温度如何，硬约束仍由程序校验。

### Q20：如何防止 Prompt Injection？

回答要点：

- 用户和攻略内容不能改变程序候选白名单。
- 工具是否调用由结构化路由和程序规则决定。
- 模型结果必须通过字段、预算、环境、地点和时长校验。
- RAG 内容被标记为可能过时的参考资料。
- 当前仍需加强：对上传内容做指令隔离、内容大小限制、恶意文件扫描和更严格的 schema 验证。

### Q21：为什么要求模型输出 JSON？

回答要点：

- 结构化输出便于解析、校验、测试和稳定渲染。
- 可以逐字段检查 `place_name`、`duration_hours` 和预算说明。
- 自由文本很难可靠判断是否用了候选外地点或超出时长。
- JSON 不是绝对可靠，所以仍需要异常处理和修复流程。

### Q22：模型 JSON 为什么还可能解析失败？

回答要点：

- 小模型可能添加 Markdown 代码块、前后说明、缺字段或类型错误。
- OpenAI 兼容的 `response_format` 在不同本地模型中的遵循程度不同。
- 当前代码先截取最外层 `{...}`，再调用 `json.loads()`。
- 生产方案可以使用 JSON Schema、Pydantic、受约束解码或 function calling。

### Q23：为什么不能把模型输出直接写入历史？

回答要点：

- 原始输出可能包含违规地点、格式错误或内部修复信息。
- 只有通过校验并转换成用户可见 Markdown 的最终答案才进入历史。
- 这样后续对话不会继续引用一次未通过验证的错误回答。

### Q24：模型连续两次输出候选外地点怎么办？

回答要点：

- 第一次失败后，把错误原因和允许地点的精确 JSON 列表发送给模型修正。
- 第二次仍失败时，不放宽白名单，也不让页面直接崩溃。
- `_fallback_plan()` 从已经通过硬约束的可信候选中生成保守计划。
- 日志记录 `plan_fallback`，页面提醒这是程序降级结果。

### Q25：为什么不无限重试？

回答要点：

- 无限重试会增加延迟、资源消耗，并可能始终得到相同错误。
- 本地模型容量有限，明确错误后再给一次机会已经足够。
- 确定性 fallback 能提供延迟上限和行为边界。

## 5. 约束与结构化计划面试题

### Q26：哪些约束由 Python 强制执行？

回答要点：

- 城市匹配。
- 室内/户外活动偏好。
- 地点消费等级不得超过用户预算。
- 单个候选的建议时长不得超过用户可用时间。
- 最终行程总时长不得超过用户可用时间。
- 行程最多三个地点。
- `place_name` 必须在程序候选白名单中。
- 必要字段、数字类型和正数时长必须合法。

### Q27：预算等级如何比较？

回答要点：

```python
{"免费": 0, "经济": 1, "适中": 2, "宽松": 3}
```

- 将离散类别映射成有序整数。
- 地点预算等级小于等于用户预算等级时才允许进入候选。
- 这是消费等级，不代表精确金额；模型不得编造具体票价。

### Q28：为什么地点需要稳定 `place_id`？

回答要点：

- 如果使用“城市+名称”作为身份，重命名会被误认为新增记录。
- 自增 `place_id` 在城市和名称修改后保持不变。
- 更新、删除和 UI 编辑状态都按 ID 精确定位。
- 业务唯一键仍可用于防止同城市同名地点重复。

### Q29：为什么 `TravelPreferences` 使用 frozen dataclass？

回答要点：

- 它是一次请求的事实快照，不应在工具之间被意外修改。
- 不可变对象更容易推理和测试。
- dataclass 自动生成初始化、比较和表示方法，减少样板代码。

### Q30：为什么还要定义 `TravelPlan` 和 `ItineraryStop`？

回答要点：

- 避免在系统内部长期传递没有字段约束的字典。
- 把解析后的可信数据与模型原始 JSON 区分开。
- `TravelPlan.to_markdown()` 集中负责展示，业务校验不依赖 UI。

### Q31：候选地点为空时怎样处理？

回答要点：

- system prompt 要求 `itinerary=[]`。
- 解析器拒绝模型凭空加入地点。
- fallback 返回空行程和可操作提醒，例如先维护地点目录。
- “没有结果”是合法业务结果，不应该用幻觉填满界面。

### Q32：如何验证总行程时长？

回答要点：

- 逐项把 `duration_hours` 转成 float。
- 拒绝非数字和小于等于零的值。
- 累加后与 `preferences.duration_hours` 比较。
- 不能只检查每个地点单独时长，因为三段各两小时可能超过总预算四小时。

### Q33：为什么实时路线不能写成公交耗时？

回答要点：

- 当前 OSRM 调用的是 `driving` profile。
- 数据语义是驾车距离和驾车时间。
- 把它描述为地铁、公交或步行属于语义错误，即使数字本身来自真实 API。

### Q34：怎样进一步强化结构化输出？

回答要点：

- 使用 Pydantic 模型和 JSON Schema。
- 使用支持严格 structured outputs/function calling 的模型。
- 对字符串长度、枚举、URL 和费用字段增加验证。
- 将验证错误分类型统计，分析模型最常违反的约束。

## 6. 实时工具面试题

### Q35：为什么要先做地理编码？

回答要点：

- 天气和路线 API 接收经纬度，不理解自然语言地点名。
- Photon 将“杭州图书馆”等字符串解析成标准名称和坐标。
- 地理编码结果被封装成 `GeoLocation`，供天气和路线复用。

### Q36：地理编码缓存解决什么问题？

回答要点：

- 连续问题可能反复查询同一城市和地点。
- 进程内字典缓存减少外部请求、延迟和公共 API 压力。
- `Lock` 保护并发读写。
- 当前缓存没有 TTL 和容量上限，长期服务需要 LRU/TTL 策略。

### Q37：为什么路线使用 OSRM Table API？

回答要点：

- 一次传入起点和多个候选坐标，返回距离和时间矩阵。
- 比逐个地点请求 Route API 减少网络往返。
- 程序再把矩阵展开成 `RouteEstimate` 列表。

### Q38：实时工具失败时为什么不直接终止请求？

回答要点：

- 天气或路线是增强信息，不应让基础地点推荐完全不可用。
- `RealTimeTravelTools.collect()` 分别捕获各工具异常。
- 错误写入 `TravelToolReport.errors`，模型和用户都能知道数据缺失。
- 这叫部分失败或优雅降级。

### Q39：外部 HTTP 请求为什么必须有 timeout？

回答要点：

- 公共服务可能无响应；没有超时会长期占用 Gradio worker。
- 超时通过 `TRAVEL_TOOL_TIMEOUT` 配置。
- 当前是单次超时，生产环境还应加入有限重试、退避、熔断和指标。

### Q40：为什么使用 `urllib` 而不是 `requests`？

回答要点：

- 当前 GET 请求简单，标准库足够，减少一个依赖。
- `_fetch_json()` 统一 User-Agent、超时和 JSON 解析。
- 若需要连接池、重试、异步 HTTP 或更复杂认证，可以换成 `httpx`。

### Q41：如何处理地理编码结果错误？

回答要点：

- 查询中同时加入地点和城市，降低同名地点误匹配。
- 将解析后的标准名称和坐标展示给用户，提高透明度。
- 工具失败会进入 errors，不伪造坐标。
- 更严格方案需要边界框、国家/城市校验和人工地点坐标库。

### Q42：能否并行调用天气和路线？

回答要点：

- 不能完全并行，因为二者都依赖地理编码结果。
- 城市、出发地和多个候选的地理编码可以并发。
- 得到坐标后，天气与路线可以并行。
- 当前实现以清晰和公共 API 压力可控为主，仍是顺序编排。

## 7. RAG 面试题

### Q43：什么是 RAG？本项目为什么需要它？

回答要点：

- RAG 是 Retrieval-Augmented Generation，即先检索外部知识，再让模型基于检索内容生成回答。
- 用户攻略不会写进模型参数，但可以在提问时作为上下文使用。
- 它能更新知识而无需重新训练模型，并保留来源。

### Q44：文档是在查询前还是查询时导入？

回答要点：

- 文档必须先导入：解析、切块、向量化并保存到 SQLite。
- 正常查询时生成查询向量，与已有文本块比较并取 Top-K，不会重新解析原 PDF。
- 例外是旧记录的 embedding 模型标识或向量维度不匹配：当前查询路径会先用已存正文批量重算旧向量。它不恢复丢失的 PDF 页码和表格结构；恢复结构需要重新导入原文件。
- 如果知识库为空，查询不会自动创造 document。

### Q45：导入一份文档经历哪些步骤？

回答要点：

1. 检查文件后缀。
2. PDF 用 Docling 输出按阅读顺序排列的结构块，保存页码、标题路径、块类型和表格单元格；其他格式转换为带章节的文本块。
3. 正文在原块内部按字符与 embedding token 长度限制切分；表格按完整行分组并重复表头，超长单行才按单元格切分。
4. 使用 `BGEEmbedding.embed_documents()` 批量生成 512 维归一化语义向量。
5. 将文档 ID、来源、块序号、正文、向量、embedding 模型标识、JSON metadata 和时间写入 SQLite。
6. 解析和全部向量编码成功后，在同一事务中删除同 document_id 的旧块并插入新块，实现覆盖更新；前置解析或编码失败不会先清空原文档。

追问：为什么不再用 `"\n\n".join(page.extract_text() ...)`？

- PDF 保存的是页面上的绘制内容，不保证有正确的段落顺序、表格或章节语义；提取阶段就可能把多栏和表格打乱。
- 拼接字符串会进一步丢掉明确的页面边界，后续切块难以恢复出处。增加换行无法解决版面识别问题。
- Docling 负责识别版面与阅读顺序，`PDFBlockParser.from_document()` 再把它转换为项目自己的 `ContentBlock`，避免业务层绑定第三方所有类型。
- 页码取自 Docling provenance，是从 1 开始的物理页码，不是印在书页上的页码；标题只保留实际识别到的内容，不用 LLM 编造章节。

追问：结构化块里有哪些内容？

```python
{
    "content": "| 地点 | 门票 |\n| --- | --- |\n| 博物馆 | 免费 |",
    "metadata": {
        "page_numbers": [2],
        "section": ["杭州攻略", "室内地点"],
        "block_type": "table",
        "block_id": "#/tables/0",
        "parser": "docling",
        "table": {
            "rows": [["地点", "门票"], ["博物馆", "免费"]],
            "header_rows": 1,
            "row_start": 1,
            "row_end": 2,
            "cells": [...],
        },
    },
}
```

- `cells` 保存原始单元格行列偏移、合并跨度等结构；`row_start/row_end` 是原表格的从 0 开始、左闭右开的行范围。
- 同一个大表拆成多个片段时保留同一个 `block_id`，用于追溯到原表。没有识别出表头时使用中性的列号，不把首条记录误当表头丢掉。
- 单行超长时，每个单元格片段重复列名并记录 `column_index`，避免把长说明直接截断。
- 页码与章节从 SQLite 检索结果传给 `KnowledgeSnippet`，再同时进入 LLM 上下文和页面来源展示。

追问：扫描件与解析失败怎么处理？

- 文本型 PDF 默认关闭 OCR；扫描件通过 `PDF_ENABLE_OCR=true` 启用本地 RapidOCR。
- 转换器懒加载、进程内共享，并通过锁限制并发，避免每个用户都创建一份解析模型。
- PDF 解析状态必须是完整成功；部分成功、空文档和转换异常不会把旧攻略覆盖掉。
- 数据库自动添加 metadata 字段，旧记录默认是 `{}`，不会虚构页码；旧文档重新导入后才有完整结构。
- Docling 也无法保证所有版面都正确，当前不自动合并跨页表格；复杂 PDF 仍需原页抽查和标注评测。

### Q46：为什么需要 chunk overlap？

回答要点：

- 关键信息可能跨越切块边界。
- 重叠能让相邻块都保留边界上下文。
- overlap 太大会增加重复内容、存储和检索噪声。
- 应根据文档结构、embedding 输入上限和生成模型上下文预算调参。
- 当前普通文本只在同一结构块内部重叠，不把不同章节或表格简单串起来；表格主要通过重复表头和按完整行分组保留上下文。

### Q47：当前 BGEEmbedding 如何工作？

回答要点：

- 使用 `sentence-transformers` 加载 `BAAI/bge-small-zh-v1.5`，首次使用才懒加载模型。
- 查询文本先加中文检索指令，文档正文不加指令，符合 BGE 的非对称检索用法。
- 文档通过 `embed_documents()` 批量编码，减少逐块调用的固定开销。
- 模型输出 512 维向量，并在编码阶段做 L2 归一化，点积等价于余弦相似度。
- 默认在 CPU 运行，可通过 `EMBEDDING_DEVICE=cuda` 使用兼容 GPU。
- 多个用户的 SQLite 命名空间共享同一个只读模型实例，避免每个用户重复占用模型内存。

### Q48：为什么选择 BGE-small-zh-v1.5，而不是原来的 HashEmbedding？

回答要点：

- HashEmbedding 主要依赖词面重合，无法可靠识别“安静书店”和“人少的阅读空间”等语义改写，还可能发生哈希碰撞。
- BGE 是面向检索训练的中文语义模型，比教学哈希向量更适合中文攻略召回。
- small 版本在效果、模型体积和 CPU 延迟之间更适合本地演示；选择它不代表对所有领域最优，仍需评测。
- 本地推理不需要云端 embedding API Key，正文和查询不离开机器。
- 代价是首次模型下载、模型内存和批量编码时间；企业场景还需比较 E5、其他 BGE 版本或云端模型。

追问：模型升级后旧向量怎么办？

- `rag_chunks` 保存 `embedding_model`，查询时检查模型标识和向量维度。
- 不一致时利用 SQLite 中保存的正文批量重算，并在同一数据库中更新向量与模型标识。
- 原 HashEmbedding 教学数据库已经删除；正式迁移也可以用离线任务重建新索引并做原子切换。

### Q49：当前向量检索的复杂度是多少？

回答要点：

- 每次查询读取全部文本块并逐个计算归一化向量的点积，等价于余弦相似度。
- 相似度计算是 `O(N * D)`，完整排序是 `O(N log N)`；还需加上查询编码、数据库读取和 JSON 解码的成本。N 是块数，D 是向量维度。
- 向量不匹配时触发的重编码是额外迁移成本，不应混入正常检索延迟来比较。
- metadata 保存页码和章节，并不会自动建立向量索引；当前也没有默认按 metadata 做 SQL 过滤。
- 小型知识库足够直观；数据增大后可比较 FAISS、Qdrant、Milvus 或 pgvector 的向量索引方案，例如 HNSW、IVF，并评测召回与延迟的取舍。

### Q50：为什么设置 `minimum_score`？

回答要点：

- 当库非空、K 为正且未设阈值时，Top-K 会返回至多 K 个最相近的结果，即使它们仍与问题无关。
- 最低分阈值用于丢弃弱相关片段。
- 当前默认值 `0.08` 是沿用的初始参数，尚未针对 BGE 和真实旅行语料校准，可能放入较多弱相关结果。
- score 不是“答案有 8% 的概率正确”，也不能把不同 embedding 模型的分数直接比较。需要用相关与不相关问题、无答案问题和实际检索指标调整阈值。

### Q51：Top-K 过大或过小会怎样？

回答要点：

- 太小可能漏掉关键信息，降低召回率。
- 太大会增加上下文长度、噪声和模型注意力分散。
- 当前限制为少量片段，并在共享库与私人库合并后按分数取前三。

### Q52：共享知识库和私人知识库怎样合并？

回答要点：

- 共享库用于兼容已有公共攻略。
- 用户上传内容进入自己的命名空间。
- 查询时先避免对同一个知识库实例重复检索，再分别取候选片段，合并后按 score 排序取 Top-K；当前不是按文档内容去重。
- 当前仅按分数合并，后续可加入来源权重、新鲜度和去重策略。

### Q53：怎样实现用户知识库隔离？

回答要点：

- 登录用户名或 Gradio session hash 先生成内部 user_id。
- user_id 再经过 SHA-256，得到不暴露原身份的 namespace。
- 每个 namespace 对应独立 RAG SQLite 文件。
- `UserKnowledgeBaseManager` 缓存每个用户的实例。

### Q54：SHA-256 是否等于加密？

回答要点：

- 不是。哈希是单向摘要，不可直接解密。
- 这里用于标识脱敏和稳定命名，不是保护数据库内容的加密措施。
- 真正保护敏感数据还需要磁盘加密、访问控制、密钥管理和传输加密。

### Q55：为什么匿名用户刷新后可能找不到之前的知识库？

回答要点：

- 匿名模式使用临时 `session_hash` 作为身份来源。
- 新页面或会话失效后 session hash 可能变化。
- 原数据库文件仍可能存在，但新会话不会自动映射到旧身份。
- 需要持久化身份时应启用认证，或实现安全的长期浏览器身份机制。

### Q56：如何防止过时攻略误导用户？

回答要点：

- RAG 报告明确标注来源和“可能过时”。
- 营业时间、票价和预约规则要求再次核实。
- 实时事实只允许来自本轮实时工具。
- 后续可给文档加入发布日期、有效期和来源可信度。

### Q57：为什么 RAG 命中的地点不能直接进入行程？

回答要点：

- 攻略内容可能错误、过时或包含恶意指令。
- 当前硬约束要求行程地点必须存在于人工维护的地点目录。
- 攻略可以影响理由和偏好理解，但不能绕过候选白名单。
- 新地点应先核实并录入地点目录。

### Q58：如何评测 RAG？

回答要点：

- 建立问题、相关文档块和标准答案集合。
- 检索指标：Recall@K、Precision@K、MRR、nDCG。
- 生成指标：答案忠实度、引用正确率、上下文相关性。
- 增加“无答案”案例，检查系统是否会拒绝编造。

## 8. 数据库与状态面试题

### Q59：项目有哪些状态？分别存在哪里？

回答要点：

| 状态 | 存储位置 | 生命周期 |
| --- | --- | --- |
| 地点目录 | `travel_assistant.db` | 持久化、系统共享 |
| 用户偏好 | `travel_assistant.db` | 持久化、按 user_id 隔离 |
| 会话历史 | Gradio `gr.State` | 当前浏览器会话 |
| 私人攻略 | `knowledge_base/users/*.db` | 持久化、按用户隔离 |
| 共享攻略 | `knowledge_base/travel_guides.db` | 持久化、系统共享 |
| 地理缓存 | Python 内存字典 | 进程生命周期 |
| 日志 | `logs/` | 文件持久化并轮转 |

### Q60：为什么对话历史不写入 SQLite？

回答要点：

- 当前需求只需要短期上下文，不需要聊天记录恢复。
- 减少隐私数据长期留存。
- 简化删除和用户隔离。
- 若要跨设备继续对话，需要单独的 conversation/message 表、权限和数据保留策略。

### Q61：`contextmanager` 在数据库连接中起什么作用？

回答要点：

- 进入 `with` 时创建连接。
- 正常结束时 commit。
- 异常时 rollback。
- 无论成功失败都 close。
- 将资源和事务生命周期集中管理，避免连接泄漏和忘记回滚。

### Q62：什么是 UPSERT？项目在哪里使用？

回答要点：

- UPSERT 表示记录不存在时 INSERT，冲突时 UPDATE。
- 用户偏好按 user_id 只保留最近一次值。
- 地点新增和按稳定 ID 更新也具有类似“新增或修改”行为。

### Q63：为什么要做旧表迁移？

回答要点：

- 早期地点表可能使用城市和名称作为联合主键。
- 新版需要 `place_id` 支持重命名。
- 启动时检测旧结构，创建新表并搬迁数据，避免用户手动删除数据库。
- 生产迁移应使用版本号、迁移脚本、备份和回滚方案。

### Q64：为什么 SQLite 连接不能简单做成一个全局连接？

回答要点：

- Web 请求可能来自不同线程。
- 全局连接容易出现线程限制、事务互相影响和长事务。
- 地点和偏好使用短连接上下文；RAG 的长连接则显式允许跨线程并用锁保护。
- 两种方式体现了不同访问模式。

### Q65：WAL 模式有什么作用？

回答要点：

- Write-Ahead Logging 允许读操作与一个写操作更好地并行。
- 写入先进入 WAL 文件，再合并回主数据库。
- 在线备份不能只复制 `.db`，否则可能遗漏 WAL 中的数据。

### Q66：如何备份这个项目的数据？

回答要点：

- 最简单可靠方式是停止服务后复制 `travel_assistant.db` 和 `knowledge_base/users/`。
- `.env` 含本地配置和认证信息，应单独安全备份，不能提交 GitHub。
- 在线备份应使用 SQLite Backup API，而不是只复制主文件。

## 9. 并发、可靠性与安全面试题

### Q67：项目中为什么使用 `Lock` 和 `RLock`？

回答要点：

- RAG 连接和实例缓存可能被多个 Gradio worker 同时访问。
- `Lock` 保护缓存字典和包装层操作。
- `RLock` 允许同一线程在嵌套调用中重复获得锁，避免自锁。
- 进程内锁不能保护多个进程，因此当前推荐单进程。

### Q68：`TRAVEL_CONCURRENCY` 控制什么？

回答要点：

- 控制 Gradio 队列同时执行的请求数量。
- 本地模型和显存资源有限，并发过高会导致内存不足或延迟恶化。
- 这不是完整限流；公开服务还需要网关级限流和每用户配额。

### Q69：如何区分可展示错误和内部错误？

回答要点：

- `ValueError`、`LookupError` 等业务输入错误可以向用户显示具体原因。
- 数据库、网络、模型等内部异常只显示通用信息和 request_id。
- 完整堆栈写入服务器日志，避免泄露路径、配置或实现细节。

### Q70：为什么日志不记录完整问题和攻略正文？

回答要点：

- 用户问题和攻略可能包含个人信息。
- 当前日志只记录事件、哈希用户 ID、请求 ID、耗时和错误类型。
- 在可观测性和隐私之间做最小化收集。

### Q71：为什么需要日志轮转？

回答要点：

- 长期运行时日志会持续增长并占满磁盘。
- `RotatingFileHandler` 限制单文件大小和备份数量。
- 生产环境还应集中收集、设置保留周期、脱敏并接入告警。

### Q72：为什么非本机监听必须配置认证？

回答要点：

- `0.0.0.0` 会让局域网其他设备访问应用。
- 页面能上传文件、修改共享地点和使用本地模型资源。
- 程序默认拒绝无认证的非本机启动，除非显式确认受信网络。
- Ollama 11434 端口不应直接暴露公网。

### Q73：`blocked_paths` 有什么作用？

回答要点：

- 阻止 Gradio 文件接口暴露 `.env`、SQLite、知识库和日志目录。
- 这是纵深防御之一，反向代理也不能把这些目录配置为静态资源。

### Q74：当前认证方案有什么不足？

回答要点：

- `TRAVEL_AUTH` 是简单的 Gradio 基础认证，适合本机或小型内网演示。
- 没有注册、找回密码、角色、令牌刷新、审计和细粒度授权。
- 地点目录管理仍对所有已登录用户可见。
- 生产化应接入 OAuth/OIDC、RBAC 和管理员后台。

### Q75：上传文件有哪些安全风险？

回答要点：

- 超大文件导致资源耗尽。
- 恶意或畸形 PDF 触发解析器漏洞。
- 文档内容可能包含 Prompt Injection。
- 文件名可能包含特殊字符或路径攻击。
- 当前有限制类型和大小；后续应做 MIME 检测、隔离解析、杀毒、内容长度限制和临时文件清理。

### Q76：怎样避免外部服务拖垮系统？

回答要点：

- 设置请求 timeout。
- 工具按需调用，不是每轮全部调用。
- 单项失败降级，不阻塞其他能力。
- 后续加入重试上限、指数退避、熔断、缓存、并发限制和服务健康指标。

## 10. 测试与评测面试题

### Q77：单元测试和评测集有什么区别？

回答要点：

- 单元测试验证函数、数据库和约束的确定性行为，失败通常代表代码回归。
- 评测集验证一组完整输入下的工具路由和计划质量。
- LLM 输出有不确定性，所以真实模型评测与离线确定性测试分开。

### Q78：当前测试覆盖了什么？

回答要点：

- 城市、室内外、预算和时长过滤。
- 解析器拒绝户外、超预算和超总时长结果。
- 模型连续生成候选外地点时的安全 fallback。
- 用户偏好隔离和私人知识库隔离。
- 中文粘贴攻略的保存和检索。
- 认证配置、匿名身份、错误脱敏和日志文件。
- 评测数据格式、离线评测和可选 Ollama 实测。
- PDF 页码、章节、表格单元格、重复表头、无表头表格、超长单元格和 token 长度限制。
- metadata 入库后关闭重开、检索和来源格式化；旧数据库增加 metadata 列后保留原记录。
- 通过 `TravelKnowledgeBase.import_file()` 和 `search()` 验证实际旅行入口确实使用结构化解析链路，而不只是孤立测试解析模块。
- PDF 部分成功、失败、空内容与导入失败后保留旧攻略。

最近验证记录（2026-10-27）：默认 `30 passed, 2 skipped`；设置 `RUN_PDF_INTEGRATION=1` 后为 `31 passed, 1 skipped`。默认跳过的是需下载解析模型的真实 PDF 测试和真实 Ollama 测试。多数结构测试使用构造的 Docling 数据与测试向量，不能据此声称真实中文 PDF 检索质量已经全面达标。详见 Q154。

### Q79：为什么真实 Ollama 测试默认跳过？

回答要点：

- 它依赖本机服务、具体模型、硬件和推理时间。
- CI 环境未必安装 Ollama。
- 单元测试应快速、稳定、可重复。
- 真实模型测试作为显式端到端评测运行。

### Q80：旅行约束评测检查哪些违规？

回答要点：

- 工具选择是否符合预期。
- 是否出现跨城市地点。
- 是否超预算。
- 是否违反室内/户外偏好。
- 是否使用候选列表外地点。
- 单地点和总行程时长是否超限。
- 不应生成行程时是否错误填充 itinerary。

### Q81：为什么需要“无候选”测试？

回答要点：

- 真实系统经常遇到数据不足。
- 这是最容易诱发模型幻觉的场景。
- 正确行为是明确无结果，而不是编造一个听起来合理的地点。

### Q82：如何测试外部 API，而不依赖真实网络？

回答要点：

- 将 Geocoding、Weather、Route 作为可注入对象。
- 使用 fake/stub 返回固定数据或抛出超时。
- 分别测试成功、部分失败、全部失败和错误结构。
- 少量集成测试再访问真实公共服务。

### Q83：如何测试 LLM 连续违规的场景？

回答要点：

- 使用 `SequencedLLM`，让前两次 `invoke()` 返回预设错误 JSON。
- 检查第二次提示是否包含允许地点名。
- 检查最终计划是否只使用可信候选并满足时长。
- 这比等待真实模型偶然犯错更稳定。

### Q84：评测还有哪些缺口？

回答要点：

- RAG 的检索指标和引用忠实度还不完整。
- 实时 API 的 mock/契约测试不足。
- 已有空 PDF、部分成功、转换失败和保留旧文档的回归测试；仍缺少覆盖复杂多栏、扫描件、跨页表格、损坏或恶意文件的完整语料集。
- 缺少并发压力、超长文档和 OCR 质量的系统评测。
- 缺少 UI 端到端浏览器测试。
- 缺少不同本地模型之间的质量、延迟和资源对比。

## 11. 部署与性能面试题

### Q85：启动过程做了什么？

回答要点：

1. 解析 host、port 和浏览器参数。
2. 配置控制台与轮转文件日志。
3. 解析认证配置并执行非本机安全检查。
4. 校验并发数。
5. 初始化地点库、默认地点和知识库。
6. 创建 LLM、工具、Agent、偏好存储和 Gradio 页面。
7. 启动带队列的 Web 服务并阻止敏感路径访问。

### Q86：为什么 `.env` 不能提交 GitHub？

回答要点：

- 可能包含认证密码、模型服务地址和本机配置。
- Git 历史中的秘密即使后续删除也可能被找回。
- 仓库只提交 `.env.example`，真实 `.env` 由部署环境提供。

### Q87：如何做健康检查？

回答要点：

- HTTP 200 只表示 Gradio 页面可访问。
- 应分层检查依赖导入、BGE 实际编码、SQLite 读写、真实 PDF 解析、Ollama 请求和外部 API。
- `check_environment.py` 检查依赖、模型配置、BGE 编码、数据库及隔离；`--live` 额外检查真实 LLM。Docling 可以导入不等于它已经完成真实 PDF 版面解析。
- 真实 PDF 解析需要显式运行 `RUN_PDF_INTEGRATION=1` 对应测试；旅行模型行为可用 `travel_evaluation.py --live` 评测。外部天气和路线仍需单独检查，不能把一项通过当作全部可用。
- 生产环境应拆分 liveness 与 readiness。

### Q88：当前性能瓶颈在哪里？

回答要点：

- 本地 LLM 推理通常是最大延迟。
- RAG 全量向量扫描随文本块线性增长。
- 地理编码多个候选当前顺序请求。
- 公共 API 网络延迟不可控。
- SQLite 单写者限制会影响大量并发写入。

### Q89：如何优化响应延迟？

回答要点：

- 使用更小或量化模型，合理限制 max_tokens。
- 缓存工具路由、地理编码和短期天气。
- 并发执行相互独立的外部调用。
- 使用 ANN 向量索引。
- 对无需知识库或路线的问题严格跳过工具。
- 记录各阶段耗时，先根据数据定位瓶颈。

### Q90：为什么推荐单进程？

回答要点：

- 当前实例缓存和锁都是进程内对象。
- 多进程会分别缓存 RAG 连接，进程锁不能互相协调。
- SQLite 虽支持多读单写，但多进程写入和迁移需要更严谨设计。
- 扩展时可把状态迁移到 PostgreSQL、Redis 和独立向量服务。

### Q91：如何容器化？

回答要点：

- Python 应用和依赖可以放入 Docker 镜像。
- SQLite、知识库和日志挂载为持久卷。
- Ollama 可作为宿主机服务或独立容器。
- 不把 `.env` 烘焙进镜像，使用环境变量或 secret。
- 增加健康检查、非 root 用户和资源限制。

### Q92：如何扩展到生产架构？

回答要点：

```text
Web/移动端
   -> API Gateway + OIDC
   -> FastAPI Agent Service
      -> Model Gateway/Ollama 集群
      -> PostgreSQL
      -> Redis 会话与缓存
      -> pgvector/Qdrant
      -> Worker Queue 文档解析
      -> Observability 平台
```

- 文档导入改成异步任务。
- 地点管理拆成管理员权限。
- 模型、工具和检索统一做超时、重试和指标。
- 数据库迁移使用 Alembic 等正式工具。

## 12. 故障场景题

### Q93：攻略保存成功，但提问时报“模型使用了候选列表之外的地点”，怎么排查？

回答要点：

1. 查看日志中的 request_id 和错误堆栈。
2. 确认 `knowledge_saved` 是否成功以及 chunks 是否大于零。
3. 单独运行 RAG search，确认问题能命中片段。
4. 检查工具路由是否 `knowledge=true`、`place_search=true`。
5. 查看程序候选地点列表。
6. 如果模型生成攻略中的未核实地点，白名单拒绝是正确行为。
7. 当前实现会明确允许地点后修正一次，再使用安全 fallback。

### Q94：保存的攻略刷新后不见了，可能是什么原因？

回答要点：

- 未启用认证时使用临时 session hash。
- 刷新、服务重启或新浏览器可能得到新身份。
- 检查 `knowledge_base/users/` 中旧数据库是否仍存在。
- 需要稳定身份时配置认证，并继续使用同一用户名。

### Q95：天气能查到，但路线为空，怎么分析？

回答要点：

- 天气只需要城市坐标；路线还需要出发地和至少一个候选地点坐标。
- 检查地点路由是否启用、候选是否为空。
- 检查出发地或候选地理编码错误。
- 检查 OSRM 返回 code、distance 和 duration 矩阵。
- 查看 `TravelToolReport.errors`。

### Q96：页面返回 200，但提问一直失败，说明什么？

回答要点：

- HTTP 200 只证明 Web 服务存活。
- Ollama 可能未启动、模型未下载或调用超时。
- SQLite 或知识库可能异常。
- 应运行环境检查和真实模型评测，并按 request_id 查日志。

### Q97：SQLite 报 database is locked 怎么处理？

回答要点：

- 检查是否存在长事务或连接未关闭。
- 确认写操作使用事务和锁。
- 降低 Gradio 并发，避免多个写任务争用。
- 文档解析与写入可改成单独 worker。
- 多进程/高并发场景迁移到服务型数据库。

### Q98：模型返回合法 JSON，但内容仍然不合理，为什么？

回答要点：

- JSON 合法只代表语法正确，不代表业务正确。
- 必须分别做 schema、字段类型、枚举、白名单和跨字段约束校验。
- 还需要离线评测和人工质量评估覆盖“合理性”。

### Q99：RAG 总能返回结果，是否说明它效果好？

回答要点：

- 不是。Top-K 即使面对无关问题也会返回最高的若干项。
- 必须看相似度阈值、相关性标注和无答案拒答表现。
- 即使使用 BGE，领域外问题也可能得到一个数值最高但实际无关的结果，因此仍需阈值、标注评测和拒答策略。

### Q100：如何定位一次请求慢在哪里？

回答要点：

- 为路由 LLM、地点查询、地理编码、天气、路线、RAG 和最终 LLM 分段计时。
- 日志中记录 request_id 和 duration_ms。
- 区分排队时间、模型推理时间和外部网络时间。
- 建立 P50/P95/P99 延迟指标，而不是只看一次请求。

## 13. 框架基础面试题

### Q101：`Agent` 基类的职责是什么？

回答要点：

- 保存名称、LLM 和消息历史等通用状态。
- 定义 `run()` 抽象接口。
- 提供增加、清空和读取消息历史的方法。
- 具体 Agent 决定怎样思考、调用工具和终止。

### Q102：SimpleAgent、ReAct、Reflection、Plan-and-Solve 有什么区别？

回答要点：

| Agent | 核心方式 | 适用场景 | 主要代价 |
| --- | --- | --- | --- |
| SimpleAgent | 单次或简单 LLM 调用 | 问答、改写 | 工具与复杂规划能力弱 |
| ReActAgent | Thought/Action/Observation 循环 | 动态工具任务 | 循环不稳定、成本较高 |
| ReflectionAgent | 执行后反思并改进 | 需要自我修正的任务 | 多次模型调用 |
| PlanAndSolveAgent | 先规划步骤，再执行 | 多步骤且可预先分解 | 计划可能与执行脱节 |

### Q103：ReAct 中 Action 和 Observation 为什么要写回当前历史？

回答要点：

- 下一轮模型必须知道刚才调用了什么工具以及结果是什么。
- `Action` 表示模型选择，`Observation` 表示环境反馈。
- 循环继续构造 Prompt，直到出现 Finish 或达到最大次数。
- 不保存 Observation，模型会重复调用或无法基于结果继续推理。

### Q104：工具注册表解决什么问题？

回答要点：

- 通过名字查找并执行工具。
- 集中维护工具描述、参数验证和错误处理。
- Agent 不需要硬编码每个具体函数。
- 后续可以按权限为不同 Agent 暴露不同工具集合。

### Q105：工具链和 Agent 有什么区别？

回答要点：

- 工具链的步骤通常预先固定，输入输出按模板传递。
- Agent 会根据当前问题动态决定下一步。
- 固定业务流程优先用工具链，可预测、易测试。
- 开放任务才需要 Agent 的动态决策能力。

### Q106：异步工具执行器适合什么场景？

回答要点：

- 多个互不依赖的 I/O 工具可以并行执行。
- 例如多个城市天气或多个独立搜索请求。
- 有依赖的步骤不能盲目并行，例如路线依赖地理编码结果。
- 还需要处理超时、取消、结果顺序和部分失败。

### Q107：`Message` 为什么要封装 role 和 content？

回答要点：

- LLM 聊天接口需要明确消息角色。
- 封装后可以统一校验、序列化和调试。
- 转成 API 请求时通常得到 `{"role": ..., "content": ...}`。

### Q108：下面代码是什么意思？

```python
for msg in self._history:
    messages.append({"role": msg.role, "content": msg.content})
```

回答要点：

- `_history` 中每个元素是 `Message` 对象。
- `msg.role` 和 `msg.content` 是对象属性。
- 循环把对象转换为 LLM API 接受的字典。
- messages 通常还包含 system 消息和本轮 user 消息，具体取决于构造顺序。

## 14. 改进设计题

### Q109：第一项最值得做的技术升级是什么？

参考回答：

- 当前已用 BGE 替换 HashEmbedding；下一步应建立 RAG 评测集，用数据调整切块、Top-K 和最低分阈值。
- 如果目标是公开部署，先做正式认证、RBAC 和管理员页面。
- 如果目标是提高稳定性，先补齐外部 API mock、超时重试、指标和告警。
- 优先级应由用户量、失败数据和目标场景决定。

### Q110：怎样支持酒店和车票工具？

回答要点：

- 为工具定义稳定输入/输出 schema。
- 区分查询和下单；下单属于高风险外部副作用，必须二次确认。
- 价格和库存具有时效性，结果需要时间戳。
- 订单操作需要幂等键、审计、重试策略和支付安全。

### Q111：怎样支持多天行程？

回答要点：

- 扩展偏好模型：日期范围、每天时间窗、住宿点和交通方式。
- 行程 schema 增加 day/date。
- 使用约束求解或优化算法处理时间、距离和开放时间。
- LLM 负责解释和偏好理解，不应单独承担组合优化。

### Q112：怎样引入真正的长期记忆？

回答要点：

- 区分短期对话、用户画像、事件记忆和文档知识。
- 只抽取稳定偏好，不把所有对话永久保存。
- 记忆写入需要用户同意、可查看、可修改、可删除。
- 检索时按相关性、时间和重要性排序。

### Q113：怎样把当前流程改成状态机？

回答要点：

- 定义节点：输入校验、路由、地点、实时工具、RAG、生成、验证、修复、降级。
- 定义条件边：工具决策、是否有候选、验证是否通过。
- 状态对象保存偏好、工具结果、错误和最终计划。
- 状态机便于恢复、可视化、观测和复杂分支管理。

### Q114：怎样减少模型幻觉？

回答要点：

- 限定候选白名单。
- 实时事实只来自工具。
- RAG 保留来源并设置最低相关度。
- 使用结构化输出和程序校验。
- 对无数据情况明确允许拒答。
- 对模型错误建立评测集并持续回归。

### Q115：怎样让项目更适合写进简历？

回答要点：

- 给出可以验证的实现和测试数字，不虚构用户量。
- 说明具体难点：动态路由、硬约束、用户隔离、RAG 和失败降级。
- 提供架构图、演示截图、运行说明和评测结果。
- 将技术选择和取舍写清楚，而不是只罗列库名。

## 15. 企业级与高并发设计题

这一部分回答“如果用户量增加、多人同时访问怎么办”。面试时先承认当前实现是单机作品集架构，再说明如何依据流量逐步演进。不要直接声称当前版本已经支持企业级并发。

### Q116：当前项目能支持多少用户同时访问？

回答要点：

- 当前没有做正式压测，不能随意给出具体用户数或 QPS。
- Gradio 设置了有限并发，本地 Ollama、显存、SQLite 写锁和公共 API 是主要瓶颈。
- “注册用户数”“在线用户数”“并发请求数”和“QPS”是不同指标，必须先明确问题。
- 应通过负载测试测量吞吐、P95 延迟、错误率、GPU 利用率和队列长度，再给容量结论。

推荐回答：

> 当前版本定位为单机演示，代码中默认把模型并发限制为 2。我不会在没有压测数据时宣称它支持多少用户。企业化时会先拆分 Web、Agent、模型、文档任务和存储，再通过压测得到每个副本的容量并进行水平扩容。

### Q117：多人同时访问时，当前架构最先遇到哪些问题？

回答要点：

- Ollama 推理吞吐有限，请求会排队，延迟明显上升。
- SQLite 允许多读，但同时只有有限写能力，知识库导入和偏好写入可能争锁。
- `gr.State` 和进程内缓存不能跨多个服务副本共享。
- Python `Lock` 只能保护当前进程，不能协调多进程或多机器。
- Photon、Open-Meteo、OSRM 公共服务可能触发限流。
- 文件解析会占用 CPU、内存和请求线程。

### Q118：企业版整体架构会怎样拆分？

回答要点：

```text
浏览器/移动端
      |
CDN / WAF / API Gateway
      |
认证服务(OIDC) + 限流 + 审计
      |
无状态 Agent API 集群
  |        |          |          |
  |        |          |          +--> 外部工具网关
  |        |          +--> RAG 检索服务 / 向量数据库
  |        +--> PostgreSQL / Redis
  +--> Model Gateway --> 多个 LLM 推理副本

文件上传 --> 对象存储 --> 消息队列 --> 文档解析 Worker --> 向量库

日志、指标、链路追踪 --> 可观测性平台
```

- Web/Agent API 尽量无状态，才能通过负载均衡水平扩容。
- 长耗时文档解析从同步请求拆到异步 Worker。
- 模型服务和业务服务分开扩容。
- 数据进入共享服务，而不是保存在单个进程内存或本机磁盘。

### Q119：为什么企业版需要把 Gradio 与 Agent API 分开？

回答要点：

- Gradio 适合原型展示，但企业前端需要更完整的路由、权限、设计系统和监控。
- FastAPI 等 API 层可以独立版本化、鉴权、限流和扩容。
- Web 前端、移动端和第三方系统可以复用同一 API。
- Agent 核心仍可以保留，只需把 UI 回调改成 API handler。

### Q120：多个服务副本之间如何共享会话历史？

回答要点：

- 不能继续依赖进程内 `gr.State`。
- 可以把短期会话存入 Redis，并设置 TTL。
- 需要长期保留时写入 PostgreSQL 的 conversation/message 表。
- 每次请求携带 conversation_id，服务端根据 tenant_id 和 user_id 校验访问权限。
- 也可以把必要上下文编码进安全 token，但不适合大段聊天记录。

### Q121：SQLite 应该如何迁移？

回答要点：

- 地点、偏好、用户、权限和文档元数据迁移到 PostgreSQL。
- 使用连接池、事务隔离、索引和正式迁移工具，例如 Alembic。
- 迁移前明确主键、唯一约束和 tenant_id。
- 采用双写、离线迁移或短暂停机方案，并做数据校验和回滚准备。
- SQLite 可继续用于开发和单机测试，不必完全删除。

### Q122：企业级 RAG 应如何升级？

回答要点：

- 当前 BGE-small-zh-v1.5 先经过领域评测，再决定保留、微调或替换，并对模型版本和索引版本做管理。
- 向量数据迁移到 pgvector、Qdrant、Milvus、Weaviate 等支持 ANN 的系统。
- 文档原文件进入对象存储，数据库只保存元数据和对象地址。
- 检索加入 tenant_id、权限标签、文档状态和版本过滤。
- 使用混合检索：关键词 BM25 + 向量召回 + reranker。
- 建立召回率、引用忠实度和无答案拒答评测集。

### Q123：如何保证企业多租户数据隔离？

回答要点：

- 每条业务数据必须包含 tenant_id，不能只依赖前端传入的 user_id。
- 身份信息来自经过验证的 access token，而不是用户可修改的普通参数。
- 数据库查询统一带 tenant_id 条件；可使用 PostgreSQL Row-Level Security。
- 向量检索也必须进行租户和 ACL 过滤。
- 对象存储路径、缓存 key、消息队列任务和日志都要包含租户边界。
- 高安全场景可以为大客户使用独立数据库、独立索引或独立部署。

### Q124：LLM 服务如何支持高并发？

回答要点：

- 通过 Model Gateway 统一管理模型、超时、重试、配额和 fallback。
- 部署多个推理副本，由负载均衡按模型和当前负载分发。
- 使用连续批处理、KV Cache 和适当量化提高 GPU 利用率。
- 对输入 token、输出 token 和并发生成数设置上限。
- 简单路由任务可以使用更小模型，最终规划才使用能力更强的模型。
- 当本地模型容量不足时，可以配置经过审批的云模型作为降级选项。

### Q125：怎样估算 LLM 容量？

回答要点：

- 先测单请求平均输入 token、输出 token、首 token 延迟和生成速度。
- 记录模型在不同并发下的 tokens/s、显存占用和 P95 延迟。
- 使用 Little's Law：`平均并发数 ≈ 到达率 × 平均响应时间`。
- 例如平均每秒 2 个请求、平均响应 8 秒，稳定系统中大约有 16 个并发请求在途。
- 还要为峰值、重试和故障副本预留容量，不能按平均流量部署。

### Q126：为什么需要消息队列？

回答要点：

- PDF 解析、OCR、切块和 embedding 可能耗时几十秒，不能长期占用 HTTP 请求。
- API 接收文件后创建任务并立即返回 task_id。
- Worker 从 Kafka、RabbitMQ、Redis Streams 或云队列消费任务。
- 前端轮询或使用 WebSocket/SSE 获取进度。
- 队列提供削峰、重试和失败队列，但任务必须设计成幂等。

### Q127：什么是背压？这个项目如何处理流量峰值？

回答要点：

- 背压是下游处理不过来时，系统限制上游继续灌入请求。
- 网关按租户和用户限流，超过阈值返回 429。
- LLM 请求进入有界队列，队列满时快速失败，不能无限占用内存。
- 文件任务按租户配额排队。
- UI 显示预计等待或繁忙状态，而不是让连接无期限挂起。

### Q128：限流可以使用哪些算法？

回答要点：

- 固定窗口：实现简单，但窗口边界可能突发。
- 滑动窗口：更平滑，但记录成本更高。
- 令牌桶：允许有限突发，适合 API。
- 漏桶：以稳定速率输出，适合保护严格下游。
- 分布式部署通常把计数放在 Redis，并按 tenant/user/model 分层限流。

### Q129：哪些内容适合缓存？

回答要点：

- 地理编码：变化少，可设置较长 TTL。
- 天气：短 TTL，例如几分钟到十几分钟，并保留观测时间。
- 路线：相同坐标和交通模式可短期缓存。
- RAG 检索：文档版本不变时可缓存 query + filters 的结果。
- 完整 LLM 回答只适合高度确定、无用户隐私的请求，缓存 key 必须包含模型版本、Prompt 版本和租户边界。
- 缓存失效和数据新鲜度比“加一个 Redis”更重要。

### Q130：分布式环境中怎样防止重复执行？

回答要点：

- 为文档导入、订单或外部副作用请求生成 idempotency key。
- 数据库使用唯一约束，重复任务返回已有结果。
- Worker 采用“至少一次投递”时，业务处理必须幂等。
- 分布式锁只在确实需要互斥时使用，不能代替数据库约束。
- 对无副作用的天气查询，重复执行通常只影响成本，不影响一致性。

### Q131：如何实现高可用和故障转移？

回答要点：

- API 服务部署多个副本，配置健康检查和滚动发布。
- PostgreSQL 使用主从、自动备份和恢复演练。
- Redis 使用高可用部署，不能把它当唯一持久数据源。
- 模型网关在某个模型不可用时切换副本或降级模型。
- 外部天气/路线失败时保留基础推荐，并明确实时数据不可用。
- 明确 RTO 和 RPO，再决定备份频率与架构成本。

### Q132：企业版应该监控哪些指标？

回答要点：

- API：QPS、P50/P95/P99 延迟、错误率、状态码和在途请求。
- LLM：首 token 延迟、总耗时、输入/输出 token、tokens/s、队列长度、GPU 利用率和显存。
- Agent：各工具调用率、路由准确率、fallback 次数、计划校验失败类型。
- RAG：检索耗时、命中率、Top-K 分数、无结果率和引用反馈。
- 数据库：连接池、慢查询、锁等待、磁盘和复制延迟。
- 业务：有效行程生成率、用户重试率和人工反馈。

### Q133：日志、指标和链路追踪有什么区别？

回答要点：

- 日志记录离散事件和错误细节。
- 指标记录可聚合数值，适合趋势和告警。
- Trace 串联一次请求经过网关、Agent、模型、RAG 和外部工具的完整调用链。
- 三者通过 request_id/trace_id 关联，才能定位“慢在哪一段”。

### Q134：怎样定义 SLO？

回答要点：

- 先定义 SLI，例如成功生成有效计划的比例、P95 响应时间和数据隔离错误率。
- SLO 示例可以是“月度 99.9% 请求不出现服务端错误”，但数字必须由业务和成本共同决定。
- 对 LLM 应区分技术可用性和答案质量，HTTP 200 不代表有效回答。
- 用 error budget 决定继续开发功能还是优先修复稳定性。

### Q135：企业数据安全还需要做什么？

回答要点：

- 全链路 TLS、数据库和对象存储静态加密。
- Secret Manager 管理密码和模型凭据，不使用明文 `.env` 分发。
- 最小权限、RBAC、审计日志和管理员操作二次确认。
- 文档内容、日志和模型请求执行隐私分类与脱敏。
- 支持数据导出、删除、保留期限和合规审计。
- 明确第三方模型和 API 是否允许接收企业数据。

### Q136：如何做压力测试？

回答要点：

- 使用 k6、Locust 或 JMeter 模拟真实请求比例，而不是只压首页。
- 分开测试天气、地点、RAG、文件导入和 LLM 规划场景。
- 逐步增加并发，找到饱和点、拐点和失败模式。
- 观察客户端延迟、服务器资源、模型队列、数据库锁和外部 API 限流。
- 做突发流量、长时间稳定性和单组件故障测试。
- 测试数据必须隔离，不能污染真实用户知识库。

### Q137：从当前版本升级企业版，应该一次性重写吗？

回答要点：

- 不建议在没有流量和瓶颈证据时一次性引入所有分布式组件。
- 第一阶段：补齐认证、监控、API 边界和压测。
- 第二阶段：把会话放入 Redis、业务数据迁移 PostgreSQL。
- 第三阶段：文档异步化并迁移向量库。
- 第四阶段：模型网关、多副本和完整容灾。
- 每一步都保留回归测试、迁移校验和回滚路径。

### Q138：请用两分钟回答“用户量上来后怎么办”？

参考回答：

> 我会先区分注册用户、在线用户、并发和 QPS，并通过压测确认瓶颈，而不是直接给出未经验证的容量数字。当前项目是 Gradio、单进程 Ollama 和 SQLite 的单机架构，最先受限的是模型吞吐、进程内会话以及 SQLite 写并发。
>
> 第一阶段我会把 UI 和 Agent API 分离，让 Agent 服务无状态化；会话放到 Redis，用户、地点和文档元数据迁移到 PostgreSQL。PDF 解析和 embedding 改为对象存储加消息队列和异步 Worker，向量检索迁移到 pgvector 或 Qdrant，并且所有查询强制带 tenant_id。
>
> 模型侧增加 Model Gateway、请求队列、token 配额和多个推理副本，根据模型 tokens/s 和 P95 延迟做容量规划。网关使用令牌桶按租户限流，队列有上限以形成背压。最后补齐日志、指标、Trace、SLO、备份恢复和故障演练。整个升级过程会分阶段进行，每一步由真实指标驱动，避免过度设计。

## 19. 结构化 PDF 与 RAG 联动专题

本节沿着“上传一份含门票表格的旅行 PDF，再依据攻略规划室内游”展开。先讲当前实现，再讲局限和可选改进；企业化方案均不代表已经落地。

### Q139：PDF 解析、embedding、向量检索和 LLM 分别负责什么？为什么不能只换一个大模型？

它们处理的是不同问题：

| 阶段 | 当前组件 | 输入与输出 | 不能替代的工作 |
| --- | --- | --- | --- |
| 版面解析 | Docling / `PDFBlockParser` | PDF → 按阅读顺序排列的结构块 | 不能保证理解所有版面，也不负责挑出与问题最相关的块 |
| 结构切块 | `chunk_blocks()` | 结构块 → 满足长度约束的小块 | 不负责事实核验或语义召回 |
| 语义编码 | `BGEEmbedding` | 文档或问题 → 归一化向量 | 不会恢复已经丢失的表格关系或页码 |
| 检索 | `RAGTool._search()` | 查询向量与库中向量 → 带 metadata 的结果 | 相似不等于真实、最新或足以回答 |
| 生成与校验 | LLM + Python 约束 | 问题、候选、工具事实和检索片段 → 合法行程 | LLM 不能凭空补齐可靠证据 |

例如解析阶段把“博物馆”和另一行“收费 100 元”错误拼在一起，BGE 可能准确编码这个错误，LLM 也可能忠实复述错误。换更大的生成模型并不能可靠修复上游事实损失。应先保证解析与来源可追溯，再评测召回和生成。

追问：能不能把整个 PDF 直接交给多模态模型？

可以作为另一种方案，但需比较上下文长度、延迟、成本、隐私和结构化输出稳定性；“传入 PDF”也要确认服务到底处理页面图像还是仅提取文本。当前项目使用本地解析加检索，不包含通用多模态整本问答功能。

### Q140：网页上传 PDF 后，代码究竟经过哪些函数？

当前调用链是：

```text
Gradio 上传事件
  -> import_knowledge_file(user_id, uploaded_file)
  -> knowledge_base_manager.for_user(user_id)
  -> TravelKnowledgeBase.import_file(file_path)
  -> rag_tool.execute("add_document", ...)
  -> RAGTool._add_document()
  -> _parse_document(path)
       PDF: self.pdf_parser.parse(path)
            -> Docling convert -> from_document -> ContentBlock
       其他格式: _convert_to_markdown -> markdown_blocks
  -> _chunk_blocks -> chunk_blocks
  -> _store_chunks -> BGEEmbedding.embed_documents
  -> SQLite rag_chunks：正文、向量、模型标识与 JSON metadata
```

`TravelKnowledgeBase.import_file()` 用文件名作为 `document_id` 和展示来源。因此同一用户库中同名文件按覆盖处理，不能误认为它已经实现了基于文件内容的版本管理。

为什么要从网页回调开始讲？因为“新增解析类并通过它的单元测试”只能证明类自身可用。只有真实入口调用它，并把结果继续传到存储与搜索，用户功能才生效。当前 `_convert_to_markdown()` 明确拒绝 PDF，防止 PDF 悄悄退回扁平字符串路径。

### Q141：提问后，PDF 的正文和 metadata 怎样进入模型与页面？

当前查询链是：

1. `TravelAssistant.reply_with_history()` 获取用户偏好、问题和最近对话，调用工具路由器。
2. 只有 `tool_decision.use_knowledge` 为真时，才检索知识库；上传成功不会强制每轮调用 RAG。
3. 用城市与问题构成查询，分别检索共享库和当前用户的私人库。`RAGTool` 生成查询向量、计算相似度并返回正文和解码后的 metadata。
4. `TravelKnowledgeBase.search()` 过滤低分结果并构造 `KnowledgeSnippet`；每个库取前三个候选，合并后再按分数取最终前三。
5. `KnowledgeSnippet.location` 通过 `format_location()` 格式化页码、章节和表格标记。
6. `build_messages()` 放入 `knowledge_report.to_context()`，模型收到正文及可用来源位置；`_request_plan()` 请求并校验行程。
7. 页面回答追加 `knowledge_report.to_markdown()`，由程序展示检索来源，不依赖模型自己记住每个引用。

注意：旅行助手的这条链路不是去调用 `RAGTool._ask()` 独立完成问答。`RAGTool._ask()` 是另一条工具问答路径，也使用带来源的上下文；排查旅行页面时应沿实际调用入口检查。

### Q142：为什么把 `content` 与 `metadata` 分开？metadata 会一起变成向量吗？

当前每条 `rag_chunks` 记录包含文档 ID、来源、块序号、正文、向量、模型标识、JSON metadata 和时间。两类内容职责不同：

- `content` 保存用于检索与回答的可读文字，包括切块时重复的章节标题、表头或列名。当前只对这些正文调用 `embed_documents()`。
- `metadata` 保存 `page_numbers`、`section`、`block_type`、`block_id`、`parser` 和表格细节，单独序列化为 JSON，检索后解码。
- 页码和原始单元格坐标属于来源定位信息，直接混入大量坐标数字可能增加编码噪声，也不利于可靠地按字段读取。

章节既能出现在正文前缀，也能出现在 metadata：前者帮助语义检索，后者帮助稳定展示，二者用途不同。当前 metadata 不参与默认 SQL 过滤，也没有单独建立索引；要支持“只搜某章节或某页”，需要增加参数、字段与查询逻辑。

追问：为什么不用一张有几十个列的关系表？

JSON 适合当前可变、嵌套的页码与表格结构，迁移成本低。如果企业场景经常按租户、文件版本、页码或类型过滤，应把高频字段独立建列并加索引；复杂表格仍可保留 JSON 或解析产物文件。

### Q143：为什么选择 Docling？pypdf、pdfplumber、PyMuPDF4LLM、MinerU 能不能用？

可以替换。选择依据是文档类型、结构要求、部署成本与实测，而不是认为一个工具对所有 PDF 都最好。

| 方案 | 可考虑的场景 | 需要核验的限制 |
| --- | --- | --- |
| pypdf | 轻量文字提取、页级处理、PDF 操作 | 对复杂阅读顺序和表格结构不能只靠字符串提取解决 |
| pdfplumber | 用文字位置、线框和规则处理可控模板的表格 | 常需针对版面调参；扫描件需另配 OCR |
| PyMuPDF4LLM | 希望从 PDF 获得便于 RAG 的 Markdown 或分页内容 | 复杂表格与多栏效果、元数据接口、版本及许可证需核验 |
| Docling | 需要统一文档结构、阅读顺序、表格单元格和出处 | 模型下载、CPU 延迟、识别误差与版本兼容 |
| MinerU 等文档解析系统 | 更复杂的中文文档、公式或版面，可作为候选评测 | 资源开销、安装、模型依赖、许可证及本机效果需核验 |

当前已经接入的是 Docling，其他工具是备选方案，没有做本项目同一语料上的横向排名。应固定工具版本，用同一组 PDF 比较阅读顺序、表格单元格与出处保留，再衡量最终问答表现。

### Q144：为什么要定义 `ContentBlock`、使用 frozen dataclass，并允许注入 PDF parser？

`ContentBlock` 是项目自己的结构契约：正文、页码、章节路径、块类型、原块 ID、表格信息和解析器来源。业务层消费这个契约，不直接依赖 Docling 的全部内部类型。

这样做有三个作用：

1. 替换解析器时写一个适配器即可，不必一起重写 SQLite、切块和页面引用。
2. `RAGTool(..., pdf_parser=...)` 可以注入测试解析器，让离线测试覆盖真实导入入口，不需要每次加载版面模型。
3. frozen dataclass 避免流程中随意重绑定字段，tuple 页码和章节也便于保持稳定。

但 `frozen=True` 不是深度不可变：内部 `table` 字典仍可能被修改。需要在拆分与序列化时留意拷贝和共享引用；不能把 frozen 等同于所有嵌套对象都线程安全。

### Q145：512 维向量是不是最多输入 512 个 token？当前如何避免切块被截断？

不是。向量维度是输出特征数，token 上限是编码器能处理的输入长度，LLM 上下文窗口又是另一项限制。

当前 `BGEEmbedding.fits_text()` 使用实际模型 tokenizer，以 `truncation=False` 编码并计入特殊 token，再与 `model.max_seq_length` 比较。`chunk_blocks()` 同时考虑字符上限和这个检查，必要时二分缩短片段，使加入章节等前缀后的完整正文也能容纳。

为什么不能只看 `len(text)`？中文、英文、标点、网址和代码的字符到 token 比例不同；固定 500 个字符不保证小于某个 token 上限。若先编码再由模型静默截断，数据库存的完整正文可能包含向量根本没有表示的后半部分。

当前限制：普通段落按长度查找切点，还没有实现按句子或语义边界优先切分；片段保留原结构块的页集合，不提供拆分后逐字符到页面的精确映射。生成模型的总上下文预算仍应另行管理，单块不过长不代表所有块加历史后一定合适。

### Q146：为什么表格不能像段落一样按固定字符切？超长表格怎样处理？

一条记录需要对应列名。例如“博物馆、免费、需预约”若被切成几个无表头字符串，检索和生成容易把票价、地点和预约条件配错。

当前处理分三层：

1. 表格能放下时保留 Markdown 表格，同时把原始 `cells`、行列关系、跨度和 caption 保存在 metadata。
2. 表格过大时按完整行分组，每组重复章节、表头和说明。未识别到表头时使用中性列名，保留首条数据，避免把它误作表头。
3. 单行也放不下时，退到按单元格拆文字，每段重复列名并记录 `column_index`、`column_header` 以及原行范围。

`row_start`、`row_end` 是原表从 0 开始、左闭右开的索引；拆出的多个块仍关联同一 `block_id`。这便于回到原始表，不等于已经实现跨页表格拼接。

追问：保存合并单元格 metadata 就能保证 LLM 理解多级表头吗？

不能。原始结构被保留，便于以后重建或检查；当前 Markdown 渲染仍可能弱化复杂合并关系。应通过真实复杂表格评测，再决定是否把层级表头展开成列路径或使用专门表格问答。

### Q147：扫描 PDF 需要 OCR 吗？启用 OCR 后是否所有 PDF 都能读对？

扫描页主要是图像，常常没有可直接提取的文字层，因此需要 OCR。当前默认关闭 OCR；可设置 `PDF_ENABLE_OCR=true` 启用本地 RapidOCR，并准备 `onnxruntime` 等依赖。版面模型默认 CPU，可通过 `PDF_DEVICE` 配置设备，`PDF_ARTIFACTS_PATH` 指定解析模型目录。

默认关闭的原因是文本 PDF 不一定需要 OCR，额外识别会增加时间和资源成本。但这不是“所有文档一律关闭”的生产策略。企业方案可识别扫描页、混合页后按需 OCR，并记录每页解析状态。

OCR 只是识别字，阅读顺序、表格关系、标题归属仍可能错误；低清、倾斜、手写和多语种文档都需单独评测。当前忽略图片块，不包含通用图表理解。空内容会提示检查 OCR，部分成功或失败会拒绝导入；没有完成扫描件识别质量的全面验证。

### Q148：显示“第 2 页”是否就证明答案有依据？页码还能有什么歧义？

当前页码来自 Docling provenance，为 PDF 的物理页，从 1 开始。封面、目录和正文可能使用不同的印刷页码，所以 PDF 阅读器的第 5 页不一定是书上印的“第 1 页”。展示和面试时必须说明这个口径。

还需区分三层保证：

- 来源定位：这个检索片段被解析为来自哪些页、哪个章节。
- 检索相关：这个片段与问题是否相关、是否包含所需事实。
- 答案支持：最终某个结论是否真的由该片段支持。

当前页面由程序追加检索来源，可靠保留了检索结果的位置；但这些来源不是逐句证据对齐，也不证明 LLM 实际使用了每一条。多页原块切分后保留原页集合，不应声称某片段中的每句话都精确属于其中某一页。

改进可以是返回结构化 `evidence_ids`、校验证据 ID 必须存在，并评测声明到证据的支持关系；只检查引用编号合法仍不足以证明内容忠实。

### Q149：旧数据库增加 metadata、重算向量和重新导入 PDF 有什么区别？

| 操作 | 解决的问题 | 无法恢复的内容 |
| --- | --- | --- |
| `PRAGMA` 检查并 `ALTER TABLE` 增加 metadata | 旧表适配新结构，默认 `{}`，保留旧记录 | 旧解析时已经丢掉的页码、章节、表格关系 |
| 模型标识或维度不匹配时重新 embedding | 让已有正文使用当前向量空间 | 原文未存下来的版面信息与 OCR 错字 |
| 从原 PDF 重新导入 | 重新解析、结构切块、编码和替换旧块 | 解析模型仍不能正确识别的内容 |

因此更新代码后，旧 PDF 不会自动出现真实页码。需要在同一用户库中从原文件重新导入；没有页码的 Markdown 或旧记录应按实际可用信息展示，不能让 LLM 猜页码。

为什么替换旧攻略要先完成解析和编码？这些步骤可能失败且耗时长。当前先准备好所有新块与向量，再用一次数据库事务替换同 document_id 的内容，避免前置失败导致原文档丢失。事务保护数据库更新，不会自动变成跨文件、对象存储或多个服务的分布式事务。

### Q150：为什么模型进程内共享并加锁？多人使用时是否已经解决并发？

每个用户独立 SQLite 库不意味着每人都应加载一份 BGE 和 Docling。共享模型实例可降低内存与初始化成本；解析器懒创建转换器，并用 `RLock` 保护转换访问。锁约束的是同一进程中的相关调用，不是集群调度器。

当前这类共享与锁并不保证高吞吐：长 PDF 仍会占用 CPU、内存和等待时间；多个进程还可能各加载一份模型。向量计算、数据库事务与页面事件也各有瓶颈，需要分开计时。

用户隔离由可信身份映射到各自知识库来实现，模型共享不能替代权限校验。可选企业方案是把解析和编码拆成受控 worker，设置队列长度、文件页数、租户配额、超时和取消机制；不要简单删锁来换速度。

### Q151：上传成功，却没有使用这份 PDF，应该检查什么？

上传成功只说明这次导入完成，并不保证每次问题都命中或被使用。建议按层检查：

1. 身份与库：上传和提问是否在同一个 user_id、数据库路径与文档 ID 下？匿名会话是否发生变化？
2. 导入产物：是否确实有记录，正文可读，metadata 有预期的页码和章节？
3. 工具路由：`use_knowledge` 是否为真？可用明确的“根据我上传的攻略……”验证意图，而不是假定任意问题都会检索。
4. 原始检索：绕开生成，直接检查查询、分数、返回正文及 metadata，区分找不到证据和模型没有用证据。
5. 过滤与合并：是否被未校准的 `minimum_score=0.08` 过滤，或在共享库与私人库合并取前三时被挤掉？
6. 消息构造：`knowledge_report.to_context()` 是否进入本轮 messages？
7. 生成与展示：模型是否采用了片段，程序追加的来源是否保留？

另外，即使检索到了“小众书店”，只要不在地点目录白名单中，就不能直接放进行程。这是业务约束生效，不一定是检索失败。需要区分“找到了攻略”“可回答其事实”和“允许生成该地点的行程”。

### Q152：新增了解析模块，为何用户仍走旧流程？这次问题如何复盘？

这次检查发现，结构化解析模块和部分下游代码已经存在，但 `wise_douctment.py` 的 PDF 导入路径仍使用旧的文本提取方式。孤立的解析功能存在，不代表正式 RAG 入口已接通；文件为何变成旧路径没有已证实原因，不应把猜测写成结论。

修复重点是让 `_add_document()` 明确经过 `_parse_document()`、结构切块和 metadata 存储，并确认搜索、旅行封装、模型上下文和页面来源连续传递这些信息。后续重构已把解析器和 RAG 合并到 `wise_douctment.py`，删除未使用的旧 `_split_markdown()`，旅行应用统一从该模块导入。排查应看实际调用关系，不能仅凭某个函数或文件存在就认定功能已接通。

另一个独立问题是运行进程：源文件已修改，不代表修改前启动的 Python 服务已经加载新代码。应核对进程命令、启动时间与端口，并在允许的操作范围内重启服务，再从原 PDF 重新导入。仅刷新浏览器不能代替后端重启；不能未经验证就说正在运行的页面已经使用新实现。

面试可概括为：我先验证入口调用链，再跟踪中间产物和持久化数据，最后核对服务运行版本；补上入口回归测试，防止以后只测模块却漏接业务链路。

### Q153：怎样写一个能防止“模块可用但没有联动”的测试？

关键是从业务入口触发，而不是直接调用想验证的私有函数。

当前 `test_travel_upload_and_search_use_structured_pdf_pipeline` 的做法是：

1. 用临时文件和临时数据库隔离测试，不修改用户攻略。
2. monkeypatch `PDFBlockParser.parse()`，返回已知带页码、章节和表格的结构数据，并记录是否收到文件。
3. 调用真实 `TravelKnowledgeBase.import_file()`，而不是直接往 `rag_chunks` 塞数据。
4. 调用真实 `TravelKnowledgeBase.search()`，检查命中的表格、页码和正文。
5. 同时断言 `report.to_context()` 与 `report.to_markdown()` 保留章节和页码，覆盖模型输入与页面来源这两个出口。

这个测试能发现旅行入口绕过 PDF parser、metadata 未保存或展示链路丢字段。由于替换了解析过程并使用测试向量，它不证明 Docling 对真实文件的识别效果，也不证明 BGE 的语义排序质量；需要另配真实组件集成测试。

```powershell
}
```

真实 LLM 测试由 `RUN_LIVE_TRAVEL_EVAL=1` 单独控制，也可运行 `python travel_evaluation.py --live`。真实 PDF 与 LLM 都依赖本地组件和模型准备状态，因此默认与快速离线回归分开。不要把测试通过率写成业务准确率、检索 Recall@K 或“支持多少并发用户”。

### Q155：只记录 embedding 模型名称足够吗？企业里怎样安全升级索引？

当前依据模型标识和向量维度判断是否需要重算，能处理常见替换情况，但相同名称或相同维度不保证向量空间和处理流程没变。例如模型 revision、查询指令、归一化设置、解析器版本或切块规则改变，都可能影响结果。

更完整的索引版本应记录：

- embedding 名称、revision、tokenizer 和向量维度；
- query instruction、归一化方式和文本预处理版本；
- parser 名称、版本、OCR 与表格配置；
- chunk 算法、字符/token 上限、overlap 和 metadata schema 版本；
- 原文件内容摘要、文档版本和租户归属。

企业升级可以保留旧索引服务读流量，在后台构建新版本，用固定评测集验证后切换索引指针，并保留回滚窗口。当前仍是查询路径内更新旧向量，没有实现双索引切换、后台迁移或完整处理流水线指纹，应作为改进方案说明。

### Q156：如何评测“结构化 PDF”真的改善了 RAG，而不是只让界面多了页码？

应把解析、检索和生成分开标注与评测，再做同样条件下的对照实验。

1. 建立包含单栏、多栏、中文标题、无表头/多级表头、合并单元格、跨页表格、扫描页和无答案问题的固定语料；标注来源页、章节、关键单元格及标准证据。
2. 解析层测阅读顺序、文字遗漏、表格行列关联、数值与单位准确性、章节和物理页定位；OCR 样本另测字符错误率。
3. 检索层测 Recall@K、MRR/nDCG、无答案误召回和重复块占比，单独检查“免费/收费”“无需/需要预约”等容易反转的条件。
4. 生成层测票价与预约事实是否被证据支持、引用位置是否正确、无证据时是否承认不知道，以及行程是否继续满足白名单与预算约束。
5. 对照旧扁平解析与结构化解析，固定 embedding、问答模型、输入问题和可比的上下文预算，同时记录导入耗时、检索延迟、内存与存储开销。

当前已有结构和联通性回归测试，没有完成上述完整质量对照。不能宣称 Docling 一定提高了某个百分比，也不能只用“来源出现了页码”作为语义正确性的证明。

### Q157：企业用户同时上传大 PDF，解析、存储和权限应该怎样设计？

以下是扩展方案，当前本地版尚未全部实现：

1. 接口校验可信身份、租户权限、文件大小、类型与页数，将原文件保存到受控对象存储，创建导入任务并返回任务 ID。
2. 队列分离上传请求与 OCR/版面解析/embedding 重任务；worker 设置资源上限、超时、重试、取消与租户配额，避免一个长文档占满服务。
3. 保存原文件摘要、解析产物和处理版本；幂等键可以包含租户、文件内容摘要与流水线版本，不能仅用文件名判断重复。
4. 新文档版本完成解析与向量构建后再发布。旧版本在新版本成功之前继续可读；失败任务记录阶段和可定位的错误，不泄露正文。
5. 统一检索必须强制携带租户与 ACL 过滤，上传、检索、下载、引用预览和删除使用一致授权规则；用户不能自行指定其他人的命名空间。
6. 监控排队时长、每页解析耗时、失败率、OCR 占比、编码吞吐、内存与索引延迟，按实测容量决定 worker 数量。

若把解析原始 `cells` 等大 metadata 在每个片段重复存储，长期会产生冗余。可把完整解析产物按 block_id 单独保存，检索记录只保留正文、出处指针和常用过滤字段；这需要额外设计引用一致性、删除和版本管理。

安全方面还应限制解析器权限、隔离工作目录并防御恶意文件。RAG 片段属于不可信数据；当前仍与规则一起组成 system 上下文，不能声称已彻底防止提示注入。改进应包括明确的数据边界、工具权限限制与恶意文档评测。

### Q158：面试官问“根据上传 PDF 推荐室内地点，门票多少，证据在哪”，如何完整回答？

可以这样回答：

> 我先在导入阶段把 PDF 解析为带物理页码、章节和表格单元格的结构块，再按表格行和 embedding 输入限制切分，使用本地 BGE 编码，正文与向量存 SQLite，出处单独存 metadata。提问时 Agent 判断是否用知识库，检索当前用户和共享库的相关片段，把正文及来源交给模型。模型规划仍只能选地点目录中的候选，Python 负责校验室内偏好、预算和时长，页面由程序追加检索来源。比如命中“某博物馆—免费—需预约”的表格行，我可以展示它来自 PDF 物理第几页、哪个章节，并对照原页检查。攻略票价可能过时，不能当作实时票务接口；若没有可靠片段就不应编造票价。当前主要验证了结构保存与联通性，复杂 PDF 质量、逐句引用校验和高并发仍需继续评测与完善。

容易被追问的边界：

- 当前应用主要输出旅行计划，不能把它描述成已实现任意文档、任意问题的通用问答产品。
- “免费”若出自攻略，就说明是文档记载并提醒核实；天气、路线工具不能核验门票。
- 如果攻略地点不在目录中，应先核实录入目录，不能让 RAG 绕过白名单。
- 如果只想问“文档里的门票是多少”，还要评测当前路由和行程 JSON 对纯事实问答的适配，必要时设计单独事实回答分支，不能声称已覆盖所有问法。
- 页面列出的来源证明检索到了这些材料，逐句事实支持仍需单独验证。
